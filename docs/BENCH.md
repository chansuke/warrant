### auto と off の差の内訳（M1-6）

`run --report` の契約カウンタ（プロファイラ付きなので時間は bench より長い）:

| モード | contract-checks | contract-ms |
|---|---|---|
| runtime | 141,524 | 114.4 |
| auto | 25,586 | 87.9 |
| off | 0 | 0 |

auto で残る検査は merge と msort の `perm?` だけで、呼び出しのたびに両方のベクタを並べ替えるので重い。
検査回数は 82% 減ったが、契約の時間は 23% しか減っていない。残りを消すには `perm?` を証明できるようにする必要がある（DESIGN.md の未決事項）。

D25 で `perm?` の2節も証明できるようになり、auto で検査する節は 0 になった（`run --report` の contract-checks は 0）。

### 入力の長さと時間の内訳（M2-0、2026-11-20）

`scripts/bench-sizes.sh "1000 2000 4000 8000" 3 -- --contracts off`（`gen` の引数を書き換えて測る）:

| n | median (ms) | vec-elems |
|---|---|---|
| 1000 | 20.7 | 1,509,062 |
| 2000 | 61.5 | 6,020,088 |
| 4000 | 202.2 | 24,044,082 |
| 8000 | 706.0 | 96,096,133 |

n を2倍にするとコピーした要素は4倍、時間は 3.0〜3.5 倍になる（O(n²)）。n=2000 の median は上の表の 57 ms より高い。コードは同じで、差の原因は調べていない。

`scripts/profile-breakdown.sh examples/msort.wrt OUT.svg 20`（perf、`bench -n 20 --contracts off`、n=2000）:

| 分類 | 割合 |
|---|---|
| コピー: `cons` の `Vec::extend` | 31.2% |
| コピー: `rest` / `slice` の `to_vec` | 17.0% |
| 解放: `Rc<Vec<Value>>` と `Value` の drop | 17.8% |
| malloc / free | 8.0% |
| `Interp::eval` | 7.9% |
| `Interp::lookup` の関数表のハッシュ | 5.2% |
| 組み込み関数の分岐、呼び出し、環境 | 5.7% |
| その他（起動、カーネル、不明） | 7.3% |

flame graph の self 時間の上位5関数（同じ条件で別に記録した perf.data を `perf report --no-children` で集計。インライン化されたコードは呼び出し元の関数に数えるので、上の表とは基準が違う。`Interp::eval` が上の表より大きいのは、eval にインライン化された clone や drop を含むためと推測している）: `Cloned<Iter<Value>>::fold`（`cons` の複製）30.3%、`<[Value]>::to_vec` 15.9%、`Interp::eval` 9.9%、`Rc<Vec<Value>>::drop_slow` 9.1%、`drop_in_place<Value>` 7.7%。

### IR のランタイム（M2-1、2026-11-20）

`scripts/bench-compare.sh main examples/msort.wrt 5`（`--contracts auto`、main と交互に5回）: main 56.3 ms → 46.0 ms（-18.4%）。M2-0 の見積もり（インタプリタ本体と名前のハッシュで 19%）とほぼ一致する。
同じビルドを交互に3回: `--contracts runtime` 144.4 / 144.8 / 147.8 ms、`--contracts off` 45.2 / 46.1 / 45.8 ms。

`scripts/profile-breakdown.sh`（n=2000）: `cons` の複製 39.4%、`rest` / `slice` の複製 20.9%、解放 12.1%、malloc / free 8.4%、`eval` 5.6%、組み込み関数の分岐 2.9%、呼び出し 0.7%、環境と名前のハッシュ 0%、その他 9.9%。残りの時間の大半はベクタの複製で、M2-2 の対象になる。

### ベクタの範囲表現と Move（M2-2、2026-11-20）

`scripts/bench-sizes.sh "1000 2000 4000 8000 16000 32000" 5 -- --contracts off`:

| n | median (ms) | vec-elems | 時間の比（n が半分のとき比） |
|---|---|---|---|
| 1000 | 5.5 | 8,552 | |
| 2000 | 11.9 | 18,102 | 2.17 |
| 4000 | 27.0 | 38,272 | 2.26 |
| 8000 | 61.0 | 80,694 | 2.26 |
| 16000 | 134.4 | 169,438 | 2.20 |
| 32000 | 306.9 | 355,256 | 2.28 |

n を2倍にすると時間は 2.2〜2.3 倍（n log n なら約 2.2 倍）。M2-0 の 3.0〜3.5 倍（O(n²)）から変わった。n=8000 は 706 ms から 61 ms。
`scripts/bench-compare.sh main examples/msort.wrt 5`（`--contracts auto`）: main 47.7 ms → 12.6 ms（-73.7%）。

`(concat acc [n])` で引数に足していく再帰（n=20000）は、Move がないと 4148 ms（2 億要素のコピー）、あると 27 ms（4 万要素）。呼び出し元のフレームが引数を持ち続けると、バッファへの参照が2つになりその場で書けないため。

`scripts/profile-breakdown.sh`（n=2000、40 回）: コピー 0.6%、解放 8.5%、malloc / free 17.8%、`eval` 23.8%、組み込み関数 11.9%、その他 34.3%（大半は引数を集める `eval_all`）。self 時間の上位は `Interp::eval` 18.3%、`Interp::eval_all` 14.8%、`Interp::builtin` 11.2%、`_int_free` 10.5%。残りは評価そのものと、呼び出しごとの引数の `Vec` とフレームの割り当てになった。
