## プロンプト本文

あなたは Warrant という言語処理系（Rust）の開発を引き継ぎます。M1（静的検証）は完成済みで、今回の仕事は **M2: 独自ランタイムと自動並列化** です。

### 最初にやること

1. `CLAUDE.md`、`docs/DESIGN.md`、`docs/M2_DESIGN.md` をすべて読む。DESIGN.md の Decision Log（D1〜D25）は確定事項なので、覆す場合は理由を Decision Log に書いてからにする
2. `cargo test --release` と `cargo clippy --release --all-targets -- -D warnings` が通ることを確認する
3. `target/release/warrant check examples/msort.wrt` で 39 VC がすべて proved になり、`bench --contracts auto` と `--contracts off` の median に差がないことを確かめる（M2 の計測に契約の時間が混ざらないことの確認）
4. `perf record` が使えるか確かめる。`kernel.perf_event_paranoid` が 2 以上なら、ユーザーに `sudo sysctl kernel.perf_event_paranoid=1` を頼む。断られたら `run --report` のカウンタで代える

### 背景（なぜこれを作るか）

Warrant は、AI が実装を書き、人間は仕様だけを承認する言語です。D9 で「純粋で検証済みの関数はコンパイラが自動で並列化してよい」と決めています。M1 で契約は実行前に証明され、msort では実行時検査が 0 になりました。

M2_DESIGN.md §0 の計測で分かったこと:

- 今の msort は O(n²)。`cons` / `rest` / `slice` が毎回ベクタを複製し、n=8000 で 9600 万要素をコピーする
- merge の再帰の深さは入力の長さに等しく、n=10^6 は深さの上限（200,000）で止まる
- だから並列化の前に、ベクタの表現と再帰の深さを直す

### M2 のタスク（この順で進める）

各タスクは、受け入れ条件を満たし、テストを足し、`cargo test --release` と clippy が通った状態でコミットする。性能に関わるコミットには、前後の `warrant bench examples/msort.wrt -n 10` の median を書く。設計の詳細は M2_DESIGN.md の該当節を見る。

#### M2-0 計測の土台（§0）

- n=1000, 2000, 4000, 8000 の msort の median と `vec-elems` を BENCH.md に表で載せる。入力の長さを変えた例題は `examples/` に置かず、bench のスクリプトで `gen` の引数を書き換えて作る
- 受け入れ条件: BENCH.md に表がある。perf が使えるなら flame graph の上位5関数を書く

#### M2-1 実行用 IR（§1.1）

- `ast::Module` を `ir::Program` にコンパイルし、スロットの環境で評価する。1スレッド、`Rc` のまま
- 実行時に検査する節は `contracts::Checks` が選んだものだけを IR に含める
- M1 のインタプリタを oracle にした差分テストを `tests/` に足す（例題と、既存の生成器で作るランダムなプログラム）。値が同じか、エラーの種類が同じこと
- `run` / `bench` の出力の形（`--report` を含む）とエラーの kind、終了コードは変えない
- 受け入れ条件: 差分テストが通る。n=2000 の median を BENCH.md に記録する

#### M2-2 ベクタの範囲表現とその場の書き換え（§1.2, §1.3）

- `VecV { buf, start, len }`。`rest` / `slice` は O(1)。`cons` / `concat` は参照が1つならその場で書き、そうでなければ余白付きで複製する
- コンパイル時に各ローカル変数の最後の使用を `Move` にする
- 共有したベクタを書き換えても、もう一方から見た値が変わらないことのテストを足す
- 新しいランタイムを `run` / `bench` の既定にする。M1 のインタプリタはテストの oracle としてだけ残す
- 受け入れ条件: n を2倍にしたときの時間が 2.5 倍以下。`vec-elems` が n log n で増える（n=1000〜8000 の表）

#### M2-3 再帰の深さ（§1.4）

- 1フレームの大きさを測り、深さの上限を上げる案（B）で n=10^6 が足りるかを見積もる。足りなければ TRMC（A）を実装する。どちらにしたかと理由を Decision Log に書く
- 受け入れ条件: n=10^6 の msort が1スレッドで動き、結果が sorted であること。median を記録する

#### M2-4 スレッドをまたげる値

- `Rc` を `Arc` にして、`Value: Send + Sync` にする
- 受け入れ条件: 1スレッドでの median の変化を BENCH.md に記録する。悪化が 10% を超えたら原因を調べて書く

#### M2-5 純粋な呼び出しの fork-join（§1.5）

- エフェクトが `[]` と推論された大域関数の呼び出しを2つ以上含む引数を `Fork` にコンパイルし、`rayon::join` で評価する（D26 で決定済み。Cargo.toml に足すのはこのタスク）
- 粒度はまず fork の入れ子の深さで切る
- 意味は逐次実行と同じにする: エラーは評価順で先のもの、純粋な関数だけを並列にする、ワーカーにも大きいスタックを与える
- `--report` はスレッドごとのカウンタを合算し、`:cpu-ms` を足す
- 受け入れ条件: 同じプログラムを 100 回並列に実行して、値とエラーが毎回同じ。n=10^6 で N スレッドが1スレッドより速い

#### M2-6 並列効率のレポート（§1.6）

- `bench --threads N` と `bench --scaling` を足す。出力は S式で、`:speedup` と `:efficiency` を含める
- 粒度（深さの閾値）を計測で決め、DESIGN.md の未決事項「並列化の粒度」を更新する
- 受け入れ条件: BENCH.md に n=10^6 の 1, 2, 4, 8, 16, 24 スレッドの表がある。8 スレッドで1スレッド比 4 倍を目標にし、届かなければ何が律速しているかを書く

#### M2-7 M1 のインタプリタの削除

- `Sexp` を評価するコードを消す。差分テストの oracle は、M2-2 以降の結果を固定した期待値に置き換える
- CLAUDE.md のコード構成の表、DESIGN.md §4〜§7 を更新する
- 受け入れ条件: `eval.rs` に `Sexp` の評価が残っていない。すべてのテストが通る

### 制約

- CLAUDE.md の不変条件（Wisp 往復、出力はすべて S式、終了コード、i64 はラップしない、エフェクト検査は推移的）を守る
- 既存の CLI の振る舞いを壊さない。オプションの追加はよい
- 迷ったら、推奨案を選んで先に進み、判断を Decision Log（D26 から）に書く。ただし、言語の意味論を変える判断（例: 並列実行でのエラーの選び方を逐次と変える）は、実装する前にユーザーに確認する
