# M2 設計: 独自ランタイムと自動並列化

最終更新: 2026-11-26（M2-0〜M2-7 完了）

M2 では、インタプリタを実行用の IR と参照カウント付きのベクタ表現に置き換え、純粋な関数呼び出しを fork-join で並列に評価する。
目標は、`msort` を n=10^6 で動かし、1スレッドと N スレッドの比（並列効率）を報告すること。
確定した判断は `docs/DESIGN.md` の Decision Log（D26 以降）に1行ずつ書く。

## 0. 出発点（2026-11-20 の計測）

D25 で `perm?` も証明できるようになり、msort の契約はすべて省略される。`--contracts auto` と `off` の median は 57.1 ms と 57.4 ms で差がない（BENCH.md）。
M2 の計測には契約の時間が混ざらない。

入力の長さを変えた `--contracts off` の計測（`bench -n 3`、`run --report` の `vec-elems`）:

| n | median (ms) | vec-elems |
|---|---|---|
| 1000 | 17.8 | 1,509,062 |
| 2000 | 56.2 | 6,020,088 |
| 4000 | 192.9 | 24,044,082 |
| 8000 | 685.3 | 96,096,133 |

- n を2倍にすると、コピーした要素数は4倍、時間は 3.4〜3.6 倍になる。今の msort は O(n²) で動いている
- 原因は `cons` と `rest` と `slice` が毎回ベクタ全体を複製すること（`eval.rs` の `to_vec` と `extend`）。merge は1回の呼び出しで `cons` と `rest` を1回ずつ呼ぶので、長さ L の merge は O(L²) 要素をコピーする
- perf で測った内訳（M2-0、`scripts/profile-breakdown.sh`、n=2000）: ベクタのコピー 48%（`cons` の `extend` 31%、`rest` / `slice` の `to_vec` 17%）、解放 18%、malloc / free 8%。この3分類の合計は 74%。ただし malloc / free は呼び出し元をほとんど辿れないので、環境のフレームなどベクタ以外の割り当ても含みうる。インタプリタ本体（`eval`、組み込み関数の分岐、呼び出し、環境）は 14%、シンボルを評価するたびに関数表を名前で引くハッシュが 5%。n=8000 では、コピー（`extend` と `to_vec`）と解放の合計が 81% になる
- merge の再帰の深さは入力の長さに等しい。`MAX_DEPTH` は 200,000 なので、n=10^6 の msort は今の書き方では `:kind stack` で止まる

IR への置き換え（M2-1）で、インタプリタ本体と名前のハッシュ（合わせて 19%）が消え、ほかの時間が変わらないと仮定すると、速くなるのは 2 割弱にとどまる（見積もり）。並列化しても O(n²) は消えず、n=10^6 は深さの上限で動かない。したがって**表現を先に直し、並列化はその後**にする。

## 1. データの形

```
ast::Module ─compile─▶ ir::Program ─▶ rt::Interp（1スレッド）
     │                     │                 └▶ rt::Pool（fork-join、M2-5）
     │                     └─ 節は contracts::Checks で選んだものだけ含める
     └─ types / effects / vc / specdiff は M1 のまま
```

### 1.1 実行用 IR（M2-1）

M1 のインタプリタは `Sexp` を評価し、変数を文字列で連結リストから探す（D16 で計測のために据え置いた）。M2 では `ast::Module` を IR にコンパイルする。

```rust
pub enum Node {
    Lit(Value),
    Local(Slot),            // フレーム内の添字
    Move(Slot),             // 最後の使用。値をスロットから取り出す（§1.3）
    Global(FnIdx),
    If(Box<Node>, Box<Node>, Box<Node>),
    Let(Slot, Box<Node>, Box<Node>),
    Call(Callee, Vec<Node>),
    Fork(Vec<Node>),        // 並列に評価する引数（M2-5）
    Lambda(Arc<LambdaIr>),  // 捕捉する変数のスロット一覧を持つ
    ...
}
pub enum Callee { Global(FnIdx), Builtin(Builtin), Value(Box<Node>) }
```

- 名前解決は `ast::lower` が済ませているので、コンパイルはスロットの割り当てと捕捉変数の計算だけになる
- 実行時に検査する節は `Checks` が選んだものだけを IR に含める。省略した節は IR に存在しない
- エラーの種類と `--report` の形は M1 と同じにする。プロファイラのフックも IR の呼び出しに付ける

### 1.2 ベクタ（M2-2）

```rust
pub enum Value { Int(i64), Bool(bool), Str(Arc<str>), Vec(VecV), Closure(Arc<Closure>), Func(FnIdx), Builtin(Builtin) }
pub struct VecV { buf: Arc<Vec<Value>>, start: usize, len: usize }
```

- `rest` と `slice` は同じ `buf` を指す範囲を返す。O(1)
- `cons x v`: `buf` を自分だけが持ち（`Arc::get_mut` が成功し）、`start > 0` なら `buf[start-1]` に書いて `start` を1減らす。それ以外は前に余白を取って複製する。余白は長さに比例させ、償却 O(1) にする
- `concat a b`: `a` の `buf` を自分だけが持ち、範囲が `buf` の末尾まであれば、その場で `b` を足す。それ以外は複製する
- 値は観測上は不変のまま。その場の書き換えは、ほかに参照がないときだけ行う

### 1.3 最後の使用での move（Perceus の再利用条件）

`Arc::get_mut` が成功するには、呼び出し元のフレームが同じベクタを持ち続けていてはいけない。
コンパイル時に各ローカル変数の最後の使用を求め、そこを `Move` にする。`Move` はスロットから値を取り出し、参照カウントを増やさない。

merge では `b` の最後の使用が `(rest b)` なので、`rest` は `b` の `buf` をそのまま受け取る。
再帰の底で返る `b` の `buf` は参照が1つになり、そこへの `cons` は前の余白（`rest` で消費した位置）に書ける。

### 1.4 再帰の深さ（M2-3）

merge は `(cons x (merge ...))` の形で、再帰呼び出しの後に `cons` が残るので末尾呼び出しではない。n=10^6 を動かす案は2つある。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. TRMC（推奨） | 末尾の `cons` を、呼び出し先に「結果を書く先」を渡す形に変換する（tail recursion modulo cons、Koka や OCaml 5 と同じ） | 深さが O(1) になる。結果を後ろへ push するので前の余白も要らない | IR の変換が1つ増える。`cons` 以外（`concat` など）には効かない |
| B. 深さの上限を上げる | `MAX_DEPTH` とスレッドのスタックを増やす | 変更が小さい | n=10^6 で 1 GB を超えるスタックが要る見込み（推測。1フレームの大きさは未計測）。並列化でワーカーごとに同じスタックが要る |

M2-3 の最初に1フレームの大きさを測り、B で足りなければ A にする。

結果（2026-11-20）: merge の1回の呼び出しは約 3,055 バイトのスタックを使った（`call_fn` の入口でスタックのアドレスを記録して測った。n=20000 と 10^5 で同じ値）。n=10^6 では約 3 GB になるので A にした（D29）。結果の位置を渡す代わりに、`cons` する値を順に溜め、最後に返ったベクタへ1回でつなぐ。実行時に ensures を検査する関数には適用しない。

### 1.5 並列化（M2-5、D9）

- 対象は、呼び出しの引数のうち、エフェクトが `[]` と推論された大域関数の呼び出しを2つ以上含むもの。msort の `(merge (msort L) (msort R))` が該当する。コンパイル時に `Fork` にする
- 粒度は、まず fork の入れ子の深さで切る（深さ `log2(スレッド数) + k` まで fork し、それより深い所は逐次）。決定的で安い。コストモデルは DESIGN.md の未決事項のまま、M2-6 の計測で決める
- スケジューラは `rayon::join`（work-stealing）を推奨する。独自の deque は、rayon のオーバーヘッドがプロファイルに出たときに書く。依存の追加なので Decision Log に書く
- スレッドをまたぐため、`Rc` を `Arc` にする。アトミックな参照カウントの1スレッドでの費用を M2-4 で測る
- 意味は逐次実行と同じにする
  - 両方の結果を待ち、エラーは評価順で先（左）のものを返す
  - 左が止まらなければ、逐次と同じく結果を返さない（右のエラーは報告しない）
  - 純粋な関数だけを並列にするので、`print` の順序は変わらない
  - 呼び出しの深さはタスクごとに数え、ワーカーのスレッドにも大きいスタックを与える
- プロファイラはスレッドごとに数えて最後に合算する。`--report` に `:cpu-ms`（全スレッドの合計）を足し、`:incl-ms` は壁時計のままにする

結果（2026-11-25、D30）: 上のとおり実装した。引数が3つ以上あるときは、真ん中の重い引数で2つに分けるだけで、それぞれの側の中はさらに分けない。fork するのは関数の本体だけで、lambda の中と契約の節は対象外。`:self-ms` は関数自身のコードの時間を全スレッドで合計したものになり、`:incl-ms` を超えうる。`vec-allocs` と `vec-elems` は1スレッドより増えることがある（D30）。`(cpu-ms X)` は Linux の `/proc/self/task/*/schedstat` から読み、ほかの OS では出さない。

### 1.6 並列効率のレポート（M2-6）

`bench --threads N`（既定は論理コア数）と `bench --scaling` を足す。
`--scaling` は1スレッドから N スレッドまでを交互に測り、`(scaling (threads 1 :median-ms T1) (threads 2 :median-ms T2 :speedup S :efficiency E) ...)` を出す。
基準 T1 は同じランタイムの1スレッドの値で、M1 のインタプリタではない。

結果（2026-11-26、D31）: 上のとおり実装した。各行に `:cpu-ms` と `:forks` も出す。粒度は深さで切ったまま、上限を `ceil(log2(スレッド数)) + 10` 段にした。n=10^6 の msort は 8 スレッドで 4.78 倍、24 スレッドで 5.74 倍。各段の時間が入力の長さに比例するとしたクリティカルパスの概算では、24 スレッドの時間の約 2/3 は順に走る外側の `merge` と入力の生成（BENCH.md）。

## 2. 検証

- 差分テスト: M1 のインタプリタを oracle にして、新しいランタイムが同じ値か同じ種類のエラーを返すことを確かめる。例題と、`tests/soundness.rs` と `tests/properties.rs` の生成器で作ったプログラムを使う。M2-7 からは、`tests/runtime_diff.rs` の例題と生成器のプログラムを、M1 との一致を確かめて書き出した `tests/runtime_diff.golden` と比べる（D32）
- その場の書き換え: 共有したベクタに `cons` / `concat` をしても、もう一方から見た値が変わらないことのテスト
- 計算量: `run --report` の `vec-elems` が n log n で増えることを n=1000〜8000 で確かめる
- 決定性: 並列実行を繰り返して、値とエラー（種類とメッセージ）が毎回同じことを確かめる
- Lean の `erasure_sound` は IR に省略した節が含まれないことと対応する。IR のコンパイルが `Checks` 以外の節を落とさないことをテストで確かめる

## 4. 決めること

- M2-2 のレビューで見つかり、残したコピー（どれも O(n) の複製が呼び出しごとに起きうる）
  - 片方の分岐でしか読まない束縛が、もう片方の分岐でもスコープの終わりまでバッファへの参照を持つ。`(let [t (rest acc)] (if c t (f (cons x acc))))` の `cons` は毎回複製する。分岐に入るときに、その分岐とその後で読まないスロットを解放すれば消える
  - クロージャの捕捉は複製で、Move しない。`(let [step (fn [] (cons n acc))] (step))` の `cons` は毎回複製する。捕捉が最後の読み出しなら移し、一度しか呼ばないクロージャの捕捉をフレームへ移せば消える

- rayon を依存に足す（D26 で決定）
- `--contracts runtime` で ensures を検査する cons の再帰は、今も深さの上限で止まる（D29）。ensures の検査をループの後に回せば外せるが、検査の順序が変わる
- 粒度: 深さで切るか、ベクタの長さなどのコストモデルを使うか（M2-6 で深さに決めた。D31）

## 5. 検討して採らなかった案

- interaction nets（HVM 系）: D8 で見送り済み
- 永続ベクタ（RRB 木）: すべての操作が O(log n) になるが、定数倍が大きく実装も重い。msort の使い方（先頭を落とす、前に足す）は範囲表現と再利用で O(1) になる
- `map` / `filter` のデータ並列: 純粋な関数を渡す `map` は自然な対象だが、M2 は呼び出しの引数の fork-join に絞る。M2-6 の後に、同じ `Fork` の仕組みで足せるかを検討する
