## プロンプト本文

あなたは Warrant という言語処理系（Rust）の開発を引き継ぎます。M1（静的検証）と M2（IR のランタイムと自動並列化）は完成済みです。今回の仕事は **M3: 人間は仕様だけを書き、エージェントが実装からマージまでを回すループ** です。

### 最初にやること

1. `AGENTS.md`、`docs/architecture.md`、`docs/DESIGN.md`、`docs/feature-map.md`、`docs/verification.md` をすべて読む。DESIGN.md の Decision Log（D1〜D32）は確定事項なので、覆す場合は理由を Decision Log に書いてからにする
2. `nix develop` の中で `scripts/verify` を実行し、`target/verify/summary.md` がすべて pass であることを確かめる
3. `target/release/warrant check examples/msort.wrt` で 39 VC がすべて proved になり、`bench examples/msort.wrt --scaling -n 3` が予算内に収まることを確かめる

### 背景（なぜこれを作るか）

DESIGN.md §1 の目的は、人間がコードをレビューせず、仕様だけを書いて承認することです。実装は、仕様を満たす根拠（warrant）が機械的に揃ったときだけマージします。M1 と M2 で、この根拠を出す道具は揃いました。

- `check`: 契約を z3 で証明する。失敗した VC は `:at` と `:counterexample` 付きの S式で返す
- `spec-diff OLD NEW`: 節ごとに weakened / strengthened / refined / new を判定し、弱めたら終了コード 1
- `bench`: `(:budget (wall-ms N))` を判定し、超えたら終了コード 3。`--scaling` で並列効率も出す
- `scripts/verify` と CI: fmt、clippy、テスト、追加行の検査、bench の退行検査

足りないのは次の3つです。

- **仕様を実装と別に書く形**: 仕様は今、実装と同じファイルの節として書かれている。`examples/msort.wrt` では、人間の仕様（`msort` の契約と `main` の予算）と、証明のためにエージェントが足した補題（`merge` の「先頭の要素」の節など）が区別できない
- **実装が仕様に従うかの判定**: 「仕様の関数がすべてあり、型が同じで、契約が仕様と同じか強く、証明済みで、予算内」を1回で判定するコマンドがない
- **ループそのもの**: エージェントを起動し、判定の結果を返して直させ、通ったら PR を作ってマージする仕組みがない

今の道具には、仕様を満たさない実装を通す穴があります。M3 の判定はこれらを塞いだうえで作る（確認済みのもの）:

- **停止性**: `ensures` は部分正しさで、停止性は `:termination assumed` のまま。`(defn f [x : i64] -> i64 (:effects []) (:ensures (> result x)) (f x))` は proved になる。`check` はこの再帰の停止を証明せず、`run` と `bench` は実際にその呼び出しを実行したときだけ深さの上限（200,000）で `stack` エラーにする。計測しない入力で停止しない実装は、どちらも通る
- **名前の上書き**: 組み込みと同じ名前の関数（`(defn sorted? ...)`）を定義でき、`check` はエラーにしない。承認した仕様の式が、実装の足した関数を指しうる
- **計測の入口**: `bench` は `main` を走らせて時間を測るだけで、結果を照合しない。実装側が `main` の入力を小さくする、定数を返すと、予算を通る
- **証明の範囲**: `check` は `unknown`、`unsupported`、z3 がない場合も終了コード 0 になりうる。契約の VC と、本体の境界・算術エラーの VC は別に扱われる
- **権限**: 同じユーザーで動くエージェントは、仕様ファイル、判定のバイナリ、証明キャッシュ（D23 はユーザーのキャッシュを信頼する）、GitHub の認証に触れられる

M2 までの作業で分かったこと:

- 毎回の milestone で、別のモデルのレビュー（Codex）が再現できるバグを見つけた。ループには「レビュー → 再現 → 修正 → テストの強化」の段を入れる
- 計測中に別の作業で負荷が上がり、数値が揺れた。予算の判定には計測の手順を決めておく必要がある

### すべてのタスクに共通する完了条件

- 受け入れ条件を満たし、テストを足す
- `scripts/verify` がすべて pass で、`target/verify/summary.md` が挙げた `docs/verification.md` の各項目を確かめた
- 証明キャッシュ、discharge、契約の省略、`formal/` に触れたら `scripts/verify formal` も通す。性能に関わる変更は `scripts/verify bench` を通し、msort の median の前後をコミットメッセージに書く
- 設計の詳細は、M3-0 で書く `docs/M3_DESIGN.md` の該当節を見る

### M3 のタスク（この順で進める）

#### M3-0 設計（`docs/M3_DESIGN.md`）

次の項目を決めて書き、**すべてをユーザーに承認してもらってから M3-1 に進む**。どれも、マージしてよい実装の意味を決めるものなので、推奨案を選んで先に進めてはいけない。

- **仕様の形**。推奨案: 仕様は別ファイル（`*.spec.wrt`）に、本体のない `defn` として書く（シグネチャと `:effects` `:requires` `:ensures` `:budget` だけ）。今は本体のない `defn` を `defn f has no body` で拒否しているので、仕様ファイルでだけ許し、`run` / `bench` は本体のない宣言を拒否し続ける。別案: 新しい形 `(spec ...)` を足す、または実装ファイルの節のハッシュを承認済みとして記録する
- **計測の入口（ハーネス）**。推奨案: 入力、呼び出す関数、結果の照合条件、予算を仕様ファイルに書き、実装側からは変えられないようにする。`bench` は実装の `main` ではなく、このハーネスを測る
- **従うの意味**。仕様の関数ごとに、`requires` は同じか弱く、`ensures` は同じか強く、`:effects` は同じか少なく、`:budget` は同じか厳しい（`spec-diff` の判定を使う）。あわせて次を決める
  - 名前: 仕様の式が指す名前（組み込みと仕様の関数）を承認時に固定し、実装がそれと同じ名前の関数を定義することを拒否する
  - 必要な証明: 仕様の関数とハーネスから到達する関数（契約の式と関数値を経るものを含む）の、契約の VC と本体の安全性の VC がすべて proved であること。`unknown`、`unsupported`、z3 がないこと、必要な VC が足りないことは、いずれも不合格
  - 外部の入口の `requires`: `verify::levels` は、呼び出し箇所のない関数、値として渡す関数、`main` の `requires` を proved にしない。「仕様の前提から実装の前提が従う」「内部の呼び出しが前提を満たす」「外部の入口では前提を実行時に検査する」を分けて定義する
  - 仕様ファイル自体の検査: ハーネスと実効のある予算があること（今のパーサは空の `(:budget)` を受け入れる）、`requires` を満たす入力があること、契約の式自体の境界・オーバーフロー
- **停止性で何を保証するか**。M3 で `(:decreases ...)` を入れて停止を証明するか、入れずに「部分正しさとハーネスの実行」をマージの条件にするかをユーザーに選んでもらう。後者なら、その保証の範囲（計測した入力でしか停止を確かめていない）を `conform` の結果に `:termination assumed` として必ず出す
- **終了コード**。`conform` の結果を表にする。既存の分類（D7、architecture.md）に合わせ、適合しない 1、SPEC / IMPL の構文・ロードの誤り 2、予算超過 3、内部エラー 101 を推奨とし、例外を作るなら Decision Log に書く
- **計測の手順**。計測するマシン、スレッド数、統計量（median）、ロードアベレージのしきい値、測り直す回数の上限を決める。上限まで有効な計測が取れなければ、合格にせず保留にする
- **信頼の境界**。エージェントが書けるのは実装ファイルだけにする。判定は、承認済みの仕様と、固定したツール（判定のバイナリ、ワークフロー）で、キャッシュなしか判定専用のキャッシュを使って行う。GitHub に書き込む認証は、エージェントとは別の実行主体が持つ
- **最初の仕様**。`examples/msort.spec.wrt` の具体的な契約とハーネス（入力の大きさ、照合条件、予算）

受け入れ条件: M3_DESIGN.md があり、上のすべてをユーザーが承認している。決定を Decision Log（D33 から）に書く。

#### M3-1 仕様ファイル

- M3-0 で決めた形を読めるようにする。`check` は仕様ファイルの型、エフェクトの宣言、M3-0 で決めた仕様ファイル自体の検査を行う。`fmt` で Wisp と往復でき、往復した後も仕様ファイルとして検査できる
- `examples/msort.spec.wrt` を置く。人間が承認するのは `msort` の契約とハーネスだけで、`merge` は含めない
- 受け入れ条件: 往復のテスト。型の誤り、ハーネスがない、空の予算、満たす入力のない `requires` のそれぞれで仕様ファイルを拒否するテスト。`run` / `bench` が本体のない宣言を拒否するテスト

#### M3-2 `warrant conform SPEC IMPL`

- 実装が仕様に従うかを1回で判定し、結果を S式で出す。終了コードは M3-0 の表に従い、`tests/cli.rs` で固定する
- 失敗はすべて、エージェントが次に直す場所が分かる形で出す: 関数名、節、`:at`、反例、または予算との差
- 受け入れ条件: 次のそれぞれで不合格になり、理由を出すテスト
  - 仕様の関数がない、型が違う
  - `ensures` を弱めた、`requires` を強めた、`:effects` を広げた
  - 仕様の式が指す名前（`sorted?` など）を実装が定義した
  - 証明できない、`unknown`、z3 がない、本体の安全性の VC が通らない
  - 予算を超える（終了コード 3）
  - 自分を呼ぶだけの関数（停止しない）
  - 外部の入口の成功例と、内部の呼び出しが前提を破る失敗例

#### M3-3 ループのスクリプト

- `scripts/agent-loop SPEC`: 実装のない状態から始める。作業用の worktree を作り、エージェント（`claude -p` か `codex exec`。どちらを使うかは引数で選ぶ）に、仕様と固定のプロンプトを渡して実装を書かせる。`conform` を実行し、失敗したらその S式を返して直させる
- 通ったら、別のモデルにレビューさせ、指摘があれば同じループで直させる。修正が入ったら、最後のコミットに対して `conform` とレビューをやり直す。修正とレビューを合わせた試行の上限を決め、上限に達したら不合格で止める
- 判定は M3-0 の信頼の境界に従い、エージェントが書けない場所で行う
- 毎回の記録を S式で残す: 回数、各回の `conform` の結果、かかった時間、通ったかどうか
- PR の作成とマージは、GitHub に書き込む操作なので、M3-4 までは手で行う
- 受け入れ条件: 実装のない `msort.spec.wrt` から始めて、人間が実装に手を入れずに `conform` が通る。最初の不合格から最後の合格までの記録を BENCH.md か M3_DESIGN.md に載せる

#### M3-4 権限の分離（テスト用のブランチで）

- CODEOWNERS とブランチ保護で、人間の承認なしに次を変える PR をマージできないようにする: 仕様ファイル、判定のコード、ワークフロー、ハーネス、仕様と実装の対応、CODEOWNERS 自体
- 判定は、保護された側の固定したワークフローが、最新のベースにマージした状態に対して行う。必須のチェックの発行元を固定する
- リポジトリの設定を変えるので、**設定を変える前にユーザーに確認する**。この段階では main の自動マージは有効にしない
- 受け入れ条件: テスト用のブランチで、次がすべてマージできないことを確かめる: 仕様ファイルを変えた PR、判定のコードやワークフローを変えた PR、`conform` が通らない PR、チェックが走っていない・スキップした・古い PR。実装だけを変え、すべて通った PR は人手なしでマージされることも確かめる

#### M3-5 すり抜けの検査

- エージェントが仕様を満たさずに通ろうとする手口を並べ、それぞれが止まることをテストにする。少なくとも次を含める
  - 仕様ファイル、判定のコード、ワークフローを書き換える
  - 仕様の式が指す名前の関数を定義する
  - 補助関数の `requires false` で、仕様の関数の証明を空にする
  - 停止しない再帰で `ensures` を空にする（計測する入力では停止し、別の入力で停止しないものも含める）
  - ハーネスを変える、結果を定数で返す
  - 契約を `runtime-checked` のまま残し、実行時の検査で通す
  - 証明キャッシュに偽の結果を置く
- 受け入れ条件: 各手口のテストがあり、すべて止まる。止まらない手口が残るうちは、M3-6 の自動マージを有効にしない

#### M3-6 自動マージ

- M3-5 で止まらない手口がなくなり、ユーザーが承認したら、main で自動マージを有効にする。実行主体と起動の手順を M3_DESIGN.md に書く
- 受け入れ条件: 実装だけを変えた PR が人手なしでマージされ、仕様を変える PR は人間の承認の後にだけ進むことを、main で1回ずつ確かめる

#### M3-7 2つ目の仕様

- msort のほかに1つ、並列計算の仕様を人間が書き、ループで実装させる。候補: ベクタの和やヒストグラムのような分割統治の畳み込み、または二分探索。仕様の内容はユーザーに承認してもらう
- 受け入れ条件: 人間が実装に手を入れずに `conform` が通る。必要だったのに足りなかった言語機能（`fold` の不変条件、`perm?` の範囲など）を DESIGN.md の未決事項に書く

### 制約

- docs/architecture.md の不変条件（Wisp 往復、出力はすべて S式、終了コード、i64 はラップしない、エフェクト検査は推移的）を守る
- 既存の CLI の振る舞いを壊さない。コマンドとオプションの追加はよい。新しいコマンドは `docs/feature-map.md` に名前を足す
- 迷ったら、推奨案を選んで先に進み、判断を Decision Log（D33 から）に書く。ただし、M3-0 の項目と、言語の意味論を変える判断は、実装する前にユーザーに確認する
- GitHub への書き込み（PR、マージ、リポジトリ設定）は、ユーザーの指示があるまで行わない。ループのスクリプトも、既定では手元で止める
- エージェントを起動するスクリプトに、API キーなどの秘密を書かない。認証は各 CLI の既存の設定を使う

### 完了時に報告すること

- 各タスクの状態（完了 / 部分的 / 未着手）と、部分的なものは何が足りないか
- 追加した Decision Log の項目
- `msort.spec.wrt` と2つ目の仕様の全文と、ループの記録（回数、各回の `conform` の失敗の種類、時間）
- すり抜けの手口ごとの結果（止まった / 止まらない）
- 人間の手が要った箇所と、それをなくすのに何が要るか
